# wallp. — Technical requirements

Version 1.0 · 10 October 2026

## Architecture

```
React Native / Expo development build + NativeWind
   │ Google native sign-in → Google ID token
   │ HTTPS JSON API / bearer session
   ▼
Fastify + TypeScript (Node LTS)
   ├─ google-auth-library → validate identity
   ├─ PostgreSQL pool → Neon (SSL, pooled URL)
   └─ AWS S3 SDK → Cloudflare R2 + sharp image processing
```

Use an Expo development build for native Google sign-in and a local Kotlin wallpaper module. Expo Go can preview basic screens but cannot fulfill the native authentication/apply flow. Start with a pinned stable Expo SDK and install Expo-managed package versions through `expo install`. NativeWind v4/Tailwind v3 are intentionally selected for a stable Babel/Metro integration.

## Repository

- `apps/mobile`: React Native client, screens, design tokens, bundled demo artworks, local native module.
- `apps/api`: Fastify API, SQL migrations, catalog/auth/admin handlers, integration tests.
- `packages/shared`: TypeScript catalog contracts and validation schemas used by both clients.
- `docs`: PRD, TRD, plan, Google/Neon/R2 guides, Android verification checklist.
- npm workspaces and committed lockfile. No credentials in version control.

## Client

React Native, Expo, TypeScript, NativeWind, expo-image, expo-linear-gradient, react-native-svg, lucide-react-native, expo-font with bundled fonts, safe-area context. AsyncStorage stores theme and local preview likes; SecureStore stores only opaque session token. A single app state provider owns identity/catalog/likes/theme, making screen actions consistent.

Navigation is a typed, small stack for details/collections/feed/Studio and three main tabs; Android hardware back dismisses overlays and returns to the previous screen. Masonry uses FlashList v2 with two columns; the feed uses a paging FlatList. Fixed card heights prevent image reflow. Limit feed batches to nearby pages. Persist theme; do not persist private admin results outside session.

Live mode is selected by `EXPO_PUBLIC_API_URL`. Without it use bundled, original deterministic abstract artwork and local preview likes. Live guests browse but must authenticate to like. Web is a visual preview; native Google sign-in is loaded only on mobile. All critical actions have loading, disabled, error, and accessible states.

## Identity and authorization

POST `/auth/google` receives an ID token, validates using Google's library with the configured web client audience, and requires verified email. Store Google `sub` as a unique identity. Create a cryptographically random opaque bearer session, persist only SHA-256 hash in PostgreSQL, expire after 30 days. SecureStore retains raw token on device; server derives the current user on every authenticated request. Revoke current session on logout; account deletion cascades all sessions/likes.

Owner authorization is server-only, based on the exact verified Gmail address `sahilsensei.work@gmail.com`. Optionally pin `ADMIN_GOOGLE_SUB` after initial setup to resist account replacement. Neither role, email, object key, nor user ID submitted by the client is trusted. API sends `isAdmin` to govern presentation, but middleware rechecks on every Studio request. No demo auth route and no email-only login.

Use request validation, body/upload limits, rate limiting, safe error responses, parameterized SQL, redacted authorization logs, explicit CORS origin allowlist, and HTTPS in production. Never put database URLs, R2 credentials, Google client secrets, or owner bypasses in EXPO_PUBLIC variables.

## Data model

UUID keys generated by PostgreSQL/Node.

- `users`: id, google_sub unique, email, name, avatar_url, created_at.
- `sessions`: token_hash primary key, user_id cascade, expires_at.
- `wallpapers`: id, slug unique, title, mood and palette JSON (both read from the image on upload), width/height, byte_size, original_key, thumbnail_key, image_url/thumbnail_url, status (published/archived), created_at.
- `likes`: (user_id, wallpaper_id) primary key; cascades for account deletion. Count by indexed aggregation; no vulnerable client-side count increments.
- `collections`: id, title, kind curated/monthly, month optional YYYY-MM, cover_wallpaper_id nullable, created_at. Unique non-null month.
- `collection_wallpapers`: (collection_id, wallpaper_id) primary key and position.
- `features`: id, kind day/week/month, wallpaper_id, starts_at/ends_at UTC; same-kind overlap prevented by database exclusion constraint.

Index publication order, styles, collection members, likes wallpaper ID, session expiry, and feature lookup. Public reads only return published wallpapers. Archived images may remain stored; archived content is hidden from likes/catalog/collection counts.

## API contracts

All JSON errors: `{ message: string }`. Catalog items follow `packages/shared/src/index.ts`.

| Method/path                           | Purpose                                                            | Access                    |
| ------------------------------------- | ------------------------------------------------------------------ | ------------------------- |
| GET /health                           | Process health                                                     | Public                    |
| POST /auth/google                     | Verify ID token and issue session                                  | Public, strict rate limit |
| GET /me                               | Current profile and likes                                          | Session                   |
| POST /auth/logout                     | Revoke bearer session                                              | Session                   |
| DELETE /me                            | Delete account/likes/sessions                                      | Session                   |
| GET /catalog?cursor&limit             | Published wallpapers with pagination, collections, active features | Public                    |
| PUT /wallpapers/:id/like              | Idempotently like                                                  | Session                   |
| DELETE /wallpapers/:id/like           | Idempotently unlike                                                | Session                   |
| POST /admin/wallpapers                | Multipart image + validated metadata → normalized assets/publish   | Owner                     |
| PATCH /admin/wallpapers/:id           | Archive/re-publish or update metadata                              | Owner                     |
| POST /admin/collections               | Create collection with published cover                             | Owner                     |
| PUT /admin/collections/:id/wallpapers | Set published member IDs transactionally                           | Owner                     |
| POST /admin/features                  | Schedule UTC window                                                | Owner                     |

Upload is proxied through the owner API rather than trusting a public PUT URL. This MVP sacrifices direct-upload throughput for simpler, reviewable image validation and private staging. A future large-file implementation may use short-lived presigned staging uploads with a server finalize step. The API reads bounded bytes, checks magic bytes/decoded format/dimensions, rotates/re-encodes with sharp, strips metadata, creates a thumbnail, writes R2 objects with immutable cache headers, then inserts metadata. Failures clean up uploaded objects; nothing is published from arbitrary client URLs.

## Android application

Package ID `com.sahilsensei.wallp`. Local Expo module `WallpWallpaper` requires `SET_WALLPAPER`. Downloads/exports happen in JS via Expo FileSystem; native code receives an app-cache file URI, validates that file lies in the cache, decodes bounded bitmap resolution, crops to the phone display aspect ratio, and calls WallpaperManager for FLAG_SYSTEM, FLAG_LOCK, or both. Work occurs off main thread. Android 7+ supports separate lock screen. Return success only after native operation returns; errors propagate to JS. No broad storage permission for applying cached media.

iOS saves with MediaLibrary and shows manual apply instructions. Web downloads use browser flow. Never imply iOS system application succeeded.

## Features, filters, dates

Feature selection uses UTC windows; week scheduling is editorial (default Monday–Monday); day defaults 24 hours and month to the next month boundary. Features are explicitly curated, not popularity trophies. Trending sorts lifetime like count; New sorts created_at. Search/filter uses loaded catalog pages; connected client fetches all pages with a bounded page size and progressive loading. Month collections are explicit metadata. Sample dates are fixed fixture dates, not promises of current publication.

## Setup dependencies

Google OAuth web ID + Android client for debug and release SHA-1. Neon pooled Postgres URL with `sslmode=require`. Cloudflare R2 account ID, bucket-scoped access keys, public delivery domain. API must be hosted separately (Neon is database hosting only); local Android emulator uses `http://10.0.2.2:4000`. Production requires an HTTPS API host and HTTPS R2 delivery domain.

## Validation

- TypeScript compilation for API/shared and mobile.
- API tests with injected fake identity/storage and a real PostgreSQL test database when provided; verify no unsigned access, idempotent likes, owner restrictions, upload validation, overlapping features.
- Credential-free security tests for auth/admin middleware, validation, token hashing, upload boundaries, and safe configuration.
- Expo Android/web bundle export to catch Metro/NativeWind/native-import issues.
- Expo dependency check and local module autolinking inspection.
- Emulator test matrix in `docs/ANDROID_TESTING.md`, with external integration checks marked pending until credentials and emulator exist.
